# ADR-020 — Audited Stock Adjustment and Stale Snapshot Guard

Status: ACTIVE
Date: 2026-08-13

## Context

Prototype Leker already has:

- canonical physical stock balance in `inventory_stock_balances`;
- canonical movement history in `stock_movements`;
- an Operational Posting approval queue for cashier-originated `GOODS_FLOW` requests;
- a visible cashier action `Penyesuaian Stok` that was intentionally read-only pending a versioned correction contract.

Bos Cyo wants a per-store transaction-integrity policy that may later block purchases when stock is anomalous/negative so moving-average HPP is not silently based on a bad stock state. That policy needs an approved manual correction path first.

A stock adjustment cannot safely be implemented as an unguarded `+/- quantity` form because stock may change between the physical count/staging moment and management approval.

## Decision

### Correction semantics

Stock Adjustment uses **target quantity** semantics.

Cashier supplies:

- product;
- target physical quantity;
- required reason;
- optional note.

Server snapshots current canonical stock at submission and derives direction/delta.

This preserves both the observed before-state and intended after-state.

### Approval compatibility

Stock Adjustment reuses the existing V1 `GOODS_FLOW` approval envelope with payload `purpose = STOCK_ADJUSTMENT`.

Reason:

- approval ownership/authorization/idempotent posting already exists;
- rebuilding `approval_requests` solely to expand its CHECK enum adds migration risk without changing the approval capability;
- the subtype is explicit in the immutable payload and the actual canonical movement is labeled `STOCK_ADJUSTMENT`.

This does not make adjustment semantically equivalent to generic GOODS_FLOW. It only reuses the envelope.

### Stale snapshot gate

At ACC time, Inventory re-reads current stock.

If current stock differs from the staged `currentQuantitySnapshot`, the request is stale:

- no inventory mutation occurs;
- request is rejected;
- stable error `STOCK_ADJUSTMENT_STALE` is returned;
- user must submit a new request from current state.

This prevents an old physical count from overwriting later sales, purchases, production, or inventory movements.

### Posting

A valid ACC reuses the existing atomic Operational Posting batch and appends:

- quantity change in `inventory_stock_balances`;
- one `inventory_ledger_entries` row;
- one `stock_movements` row with `source_type = STOCK_ADJUSTMENT`;
- approval transition to approved/posted.

The non-negative stock database invariant remains unchanged.

### Costing boundary

V1 corrects quantity only. It does not rewrite Average Cost or historical HPP snapshots.

Valuation consequences of a gain/loss adjustment are a separate Inventory/Costing + Accounting interpretation problem and must not be guessed by this correction flow.

### Accounting boundary

No Accounting journal is generated by this ADR.

The existing `wh_opname` Accounting Settings category cannot be posted until signed gain/loss branch semantics and valuation are explicitly defined. Inventory emits the correction fact; Accounting owns journal interpretation later.

## Consequences

Positive:

- cashier gets a real correction path before stricter transaction policies are enabled;
- one canonical stock source remains in use;
- adjustment history is distinguishable from generic goods flow;
- stale physical counts cannot overwrite newer inventory facts;
- no approval-table rebuild is required;
- HPP history is not silently rewritten.

Costs/constraints:

- V1 target quantity remains integer until the canonical fractional inventory migration;
- a stale request must be resubmitted;
- Accounting impact of stock gain/loss remains intentionally unposted until valuation semantics exist.

## Rejected Alternatives

### Direct cashier stock write

Rejected because it bypasses approval, audit, and official stock movement history.

### New standalone stock-adjustment balance table

Rejected because it would create a second stock source of truth.

### Treat target quantity as an unconditional overwrite at ACC

Rejected because it can erase stock changes that happened after the count was staged.

### Rewrite Average Cost during adjustment

Rejected because quantity correction alone does not define valuation meaning.

### Create a new approval request type by rebuilding the approval table

Rejected for V1 because `GOODS_FLOW` already supplies the required approval envelope and an explicit payload purpose plus stock movement source preserves the subtype semantics with less migration risk.
